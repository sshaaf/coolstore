## Current Application Summary

The repository is a **Java EE 7 monolith** ("CoolStore") built as a single Maven `war`
artifact (`ROOT.war`) and deployed to **JBoss EAP 7.4**. It implements a small
e-commerce storefront: a catalog of products with per-location inventory, a shopping cart
with promotions and calculated shipping, and an order pipeline that publishes orders to a
JMS topic and persists them to PostgreSQL. The presentation layer is a vendored
AngularJS 1.x + PatternFly single-page application shipped inside the WAR, with optional
Keycloak-based single sign-on.

Functionally the application is small and clean: **1,785 lines of Java** across **26
application classes** (plus 3 hand-written `weblogic.*` API stubs), split into five
packages. Most complexity is concentrated in a handful of methods
(`ShoppingCartService.priceShoppingCart`, `CartEndpoint.dedupeCartItems`,
`Transformers.shoppingCartToJson`) and in the container integration surface (JNDI, EJB
interfaces, JMS destinations, JPA datasource) rather than in business logic. There are
**no automated tests** (`maven.test.skip=true`), no CI/CD pipeline for OpenShift, and
database schema + seed data are managed by Flyway SQL migrations at application startup.

**Architecture:**

- **Single deployable monolith**, layered: `rest` (JAX-RS resources) → `service`
  (EJB business components) → `persistence`/`model` (JPA entities + DTOs) → PostgreSQL.
- **Five Java packages (rgctl package communities):** `rest` (4 classes),
  `service` (10), `model` (8), `utils` (4), `persistence` (1).
- **Request flow:** SPA → `/services/products`, `/services/cart`, `/services/orders`
  → `ProductEndpoint` / `CartEndpoint` / `OrderEndpoint` → `ProductService`,
  `ShoppingCartService`, `OrderService`, `CatalogService`, `PromoService`,
  `ShippingService` → `EntityManager` (via `Resources` producer) → PostgreSQL.
- **Order flow (asynchronous):** `ShoppingCartService.checkOutShoppingCart` →
  `ShoppingCartOrderProcessor.process` → `JMSContext` producer → topic `topic/orders`
  → `OrderServiceMDB.onMessage` → `OrderService.save` (JPA) +
  `CatalogService.updateInventoryItems` (inventory deduction).
- **Integration points:** PostgreSQL (JTA datasource), ActiveMQ Artemis topic,
  Keycloak OIDC (frontend), Flyway migrations (`db/migration/V1_1`, `V1_2`),
  and three legacy *container/vendor* couplings that must be removed:
  1. JNDI self-lookup of the remote EJB `ejb:/ROOT/ShippingService!...` using

     (`ShoppingCartService.lookupShippingServiceRemote`);

     `weblogic.i18n.logging.NonCatalogLogger`, satisfied by in-repo stubs under
     `src/main/java/weblogic/**`;
  3. WebLogic JNDI/T3 client code in `InventoryNotificationMDB`
     (`weblogic.jndi.WLInitialContextFactory`, `t3://localhost:7001`) — currently
     **dead code** (no `@MessageDriven` annotation, never instantiated).

## Migration Approach

**Strategy:** **Phased in-place re-platforming** — a single codebase migrated bottom-up in
dependency order, deployed as one container. This is deliberately **not** a strangler-fig
service decomposition.

**Reasoning:**

- The application is ~1.8k LOC in one deployable with a single consumer (its own bundled
  SPA). Splitting into microservices would multiply operational cost with no scaling or
  team-autonomy benefit; the only genuinely separable concern (order/audit processing) is
  already asynchronous via JMS.
- rgctl shows **5 cohesive Java packages, zero Java package cycles, and zero high
  blast-radius functions**, so a bottom-up rewrite can proceed package by package with
  low regression risk: `model` → `persistence` → `utils` → `service` → `rest` →
  messaging/audit → web assets.
- The only hard ordering constraint is the source/target *javax → jakarta* namespace
  flip, which is all-or-nothing per compilation unit: the codebase must be converted in
  one coordinated step (all 196 imports), then compiled before behaviour is restored.
- A parallel run is still recommended for cutover: keep the legacy `ROOT.war` on JBoss EAP
  reachable while the Quarkus version is validated, then switch the Route.

**Phases:**

1. **Foundation (build + namespace flip):** Quarkus BOM, Java 21, `javax.*` → `jakarta.*`,
   extension set, remove WebLogic stubs, make the project compile and package as a
   Quarkus fast-jar.
2. **Data layer:** JPA entities + datasource + Flyway extension + seed parity on
   PostgreSQL.
3. **Business services:** pricing/promotions/shipping/catalog/order services as CDI beans,
   EJB/JNDI/remote-interface removal, cart state externalized.
4. **Messaging + audit:** Artemis producer/consumer for `topic/orders`, audit-logging v2
   (record-based events over TCP), inventory deduction semantics preserved.
5. **API + web:** REST resources under `/services` with identical contracts, static SPA
   served from `META-INF/resources`, OIDC wiring, health endpoints.
6. **Quality gates:** characterization/unit/integration/E2E tests, performance baseline.
7. **Containerize + deploy:** Containerfile, OpenShift manifests, config/secrets,
   cutover and rollback runbook.

**Key Considerations:**

- **Contract preservation:** the SPA hard-codes `/services/cart`, `/services/products`,
  `/services/orders` (`src/main/webapp/app/services/*.js`). Keep every path, verb, and
  JSON shape byte-compatible so the frontend needs no change except `coolstore.json`.
- **Statefulness is the #1 architectural change.** `CartEndpoint` is `@SessionScoped` and
  `ShoppingCartService` is `@Stateful` with a per-user `ShoppingCart` field; `index.jsp`
  forces an HTTP session. Quarkus RESTEasy Reactive has no servlet session semantics, so
  cart state must move out of the JVM (Redis) or the pod cannot scale or restart safely.
  `cartId` is already a path parameter, so the refactor is mechanical.
- **EJB → CDI transaction semantics:** `OrderService.save` + `CatalogService.update`
  currently run in container-managed transactions. In Quarkus, add explicit
  `@Transactional` on the write methods to keep order+inventory updates atomic where the
  original attempted to.
- **JMS:** the topic is consumed by `OrderServiceMDB`; keep the same message body (the
  JSON produced by `Transformers.shoppingCartToJson`) so the pipeline stays
  wire-compatible with any external consumer.
- **Audit library v2 is a breaking API jump, not a version bump:**
  `FileSystemAuditLogger` is gone → `StreamableAuditLogger(AuditConfiguration)` streaming
  JSON over TCP; `AuditConfiguration.setLogDirectory("./device-inventory-audit-logs")`
  becomes `setStreamHost/setStreamPort` (defaults `localhost`/TCP, plus buffer size and
  reconnect interval); `AuditEvent` becomes a **14-component Java record**
  (`timestamp`, `event_type`, `user_id`, `session_id`, `application`, `component`,
  `action`, `resource`, `result`, `message`, `details`, `correlation_id`, `source_ip`,
  `user_agent`) with no `builder()`; `logEvent` is deprecated → `logEventAsync`
  returning `CompletableFuture<Void>`, plus `logEventAsyncSafe()` and `isReady()`.
  v2.0.0 also pulls Jackson `databind` + `jackson-datatype-jsr310` and SLF4J, and requires
  **Java 21**.
- **Dependency hygiene:** the WAR declares the audit library with `<scope>system</scope>`
  and `systemPath` — this does not work under Quarkus packaging or Quarkus Dev Services;
  it must be installed into a real repository. `maven.test.skip=true` must be removed so
  tests can run.
- **Data migration:** schema and seed rows are Flyway-managed SQL, so PostgreSQL content
  itself does not change. Flyway baseline must be respected (`baselineOnMigrate`) when
  pointing at an existing database, otherwise `baseline()` + `migrate()` ordering differs
  from the legacy startup bean.
- **Dead/legacy code to delete, not port:** `weblogic/**` (3 stubs), `StartupListener`,
  `InventoryNotificationMDB` (WebLogic T3, never activated), `ShippingServiceRemote`'s
  JNDI lookup. Deleting them removes the last vendor couplings flagged by the analysis.

## Constraints and Risks

**Constraints:**

- CI/CD is owned by the migration platform (Tekton on OpenShift): **do not create or
  modify any file under `.github/workflows/`**.
- The audit-logging library must be upgraded to **2.0.0**, which forces **Java 21**.
- The vendored AngularJS frontend and `bower_components` are **out of scope** for rewrite;
  they must keep working as-is (do not modernize the SPA in this migration).
- The two `lib/*.jar` artifacts are the only source of the audit library locally; there is
  no network access to a public release of `com.enterprise`.
- No team/timeline data available — estimates in the plan are derived from code size and
  assume 1–2 engineers.

**Risks:**

| Risk | Impact | Mitigation |
|---|---|---|
| `javax.*` → `jakarta.*` mass rewrite breaks subtle APIs (JAX-RS provider, JMS config properties, Criteria API) | High | Mechanical conversion first, compile, then fix by package; rely on characterization tests |
| Stateful cart (`@Stateful` + `@SessionScoped` + JSP session) has no direct Quarkus equivalent | High | Externalize to Redis keyed by `cartId`; add restart/multi-replica test |
| Audit library v2 API is a redesign (record `AuditEvent`, TCP streaming, no file logging) | High | Read the v2 class metadata, write a thin adapter, target a stub TCP listener in tests, configure stream host/port per environment |
| System-scope jar cannot be resolved by Quarkus build | Medium | `mvn install:install-file` into the build repository as a documented prerequisite; fail the build early if missing |
| EJB transaction boundaries lost in CDI migration (order save + inventory update) | Medium | Explicit `@Transactional`; integration test that forces a failure mid-flow |
| JMS/Artemis client configuration differs from JBoss-managed `java:/topic/orders` | Medium | Keep destination name `topic/orders`, externalize URL/credentials; test with Artemis Dev Services |
| Flyway baseline mismatch on an existing database | Medium | `baselineOnMigrate=true` + `baselineVersion=1.1`, verify on a restored dump |
| Vendored JS dominates the graph (97% of functions) and can mask Java signals | Low | Scope all analysis with `--lang java` / `--scope com.redhat.coolstore`; ignore `bower_components` in reviews |
| Hardcoded credentials in README/`keycloak.json` (`postgresPW`, `localhost:8081`) | Medium | Move to OpenShift `Secret`/`ConfigMap`; scrub README examples |
| Keycloak client config (`realm-export.json`, `keycloak.json`) drifts | Low | Treat realm export as a fixture; document required realm/client settings |

## Assumptions

These were inferred (no interactive clarification available) and must be confirmed:

1. **Target framework is Quarkus 3.x on Java 21**, not Spring Boot — justified by the
   in-repo Konveyor `quarkus-profile`, the `quarkus3`/`jakarta-ee` rule labels, and the

6. **PostgreSQL is retained** (no database engine change) and existing data is migrated by

7. **`audit-logging-library:2.0.0` is the approved target version** and its TCP stream is
   consumed by an existing central audit collector reachable from the cluster; if not,
   audit events must be routed to a stub/collector deployed with the app.

9. **Zero-downtime cutover is desired but a short maintenance window is acceptable** for
